# Восстановление SSH Mini — 2026-11-01

Последующая проверка02.11 подтвердила сетевой вход на новой загрузке через Pi;
см. [актуальное ревью](FOLLOWUP_REVIEW_2026-11-02_RU.md). Ниже сохранён результат
именно первого восстановления01.11, когда cold boot ещё не проверялся.

## Результат

На подключённой USB Mini выполнены root-ADB диагностика и восстановление
ранее разрешённого key-only root SSH2222. По SSH через временный локальный
ADB-forward подтверждены закреплённый host key и `uid=0(root)` с прежним
клиентским ключом; попытка без авторизации отвергнута. Forward удалён.
Сетевой путь через Pi в этом восстановлении не проверялся.

Постоянный init добавлен, но **cold-boot автозапуск пока не проверен**.
Нельзя обещать сохранение своего init после любого будущего обновления rootfs.

## Почему присланный диагноз требовал проверки

В журнале предполагалось, что S98 запускался до создания `/data`. Фактически
на живом устройстве `/etc/init.d/S98mini_ssh` отсутствовал вообще, а каталог
`/bkupgrade/data/opt/mini-ssh` с бинарниками и credentials сохранился.
Непосредственно запускать при загрузке было нечего.

Текущая версия: `1.372.4.21.4818318323.20261030`, ядро4.9.68. Ранее проверенный
инвентарь: `1.359.4.25.4399410546.20260720`. Это согласуется с заменой системных
файлов при обновлении; точный механизм удаления init не установлен.

Старый архив, напротив, фиксировал успешный cold boot S98 на старой версии.
Поэтому объявлять `/data` единственной доказанной причиной было неверно.

## Проверенный порядок загрузки

- `/etc/inittab` вызывает `mount -a` перед `/etc/init.d/rcS`.
- `rcS` синхронно перебирает `/etc/init.d/S??*`.
- `S99onboot.sh` создаёт `/data → /bkupgrade/data`, если каталога нет.
- Vendor `run.sh` запускает launcher в фоне и возвращается.
- `S99mini_ssh` по-прежнему сортируется **перед** `S99onboot.sh`.
- Выбрано имя `S99zzmini_ssh`, которое сортируется после onboot, и прямой
  persistent DIR `/bkupgrade/data/opt/mini-ssh`.

## Что изменено

Создан только `/etc/init.d/S99zzmini_ssh`, mode0700. Это сохранённый ранее
проверенный service script с новым DIR и поясняющими комментариями.
Запущен существующий source-built Dropbear с теми же параметрами:
key-only root, порт2222, парольная авторизация/forwarding отключены.

Исходник: [S99zzmini_ssh](../scripts/device/S99zzmini_ssh).
SHA256: `3487b3df9702ddc7d96b1a8b9d7743581bc8c9729fc934840f3f5b378b8fa058`.
Установка через скрытый staging, проверку hash/syntax и публикацию без
перезаписи существующего regular-file destination; данные синхронизированы.

Сами binary/host key/authorized keys не заменялись. Перед установкой бинарники
сверены с прежним manifest, проверены root ownership/permissions каталогов.
После установки hashes rcS/inittab/onboot/run и credential-файлов совпали
с preflight. OTA, firmware images, сеть и штатные службы не редактировались.

## Проверки и ограничения

- Четыре новых offline-теста: shell syntax, реальный shell glob/order/start,
  disabled marker и отсутствие обязательных файлов. Все прошли.
- Общий корневой suite:12passed. Fixtures не запускают настоящий daemon.
- Живой start/status и повторный start проверены, duplicate процесса нет.
- Успешный pinned-host-key SSH login и отказ без auth проверены.
- USB root-ADB сохранился, временный ADB-forward удалён.
- Перезагрузка/отключение питания не выполнялись; RAM/звук/полный диалог
  и доступность2222 с Raspberry этим опытом не проверялись.

Backup текущих пяти init/version файлов, preflight, installer, manifest и
ограниченные SSH-журналы сохранены приватно:
`.private/alice-mini/reviews/2026-11-01/ssh-recovery/`.
При ошибке installer удаляет только совпадающий по hash собственный init и
останавливает только свой подтверждённый процесс. Существующие credentials
и каталог данных сохраняет. Такой аварийный откат в успешном запуске не
выполнялся и не заявляется отдельным живым тестом.
