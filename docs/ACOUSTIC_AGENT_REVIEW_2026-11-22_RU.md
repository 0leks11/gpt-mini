лаборатории есть схема и API 33 настроек, локальный JSON import/export и живые

## Замечания код-ревью

### F1 · P1 · Shadow сбрасывает историю KWS на каждом чанке

`src/main.rs:1408–1412` безусловно вызывает `gate.reset_gate()` для каждого
чанка в shadow. Через `src/wakeword/keyword.rs:235–240` вызывается
`Rustpotter::reset`, очищающий MFCC-окно (`vendor/rustpotter-ref/src/detector.rs:279–284`).
Детектор не может накопить слово; нулевые счётчики нельзя принимать за отсутствие
ложных срабатываний или за качественную калибровку.

Временный host-fixture с настоящим InputGate и оконным fake detector, которому
нужны три чанка, воспроизвёл production-последовательность:
`normal_hits=1`, `shadow_hits=0`. Это доказательство ошибки жизненного цикла,
не тест акустического качества настоящей записи.

Исправление: сохранять историю до события, отдельно запретить облачный dispatch;
проверить непрерывный positive/negative replay в shadow и обычном режиме.

### F2 · P1 · Частичный API-профиль незаметно восстанавливает defaults

`ApplyPayload.settings` (`src/acoustics.rs:50–55`) использует тип конфигурации
с `#[serde(default)]` (`src/config.rs:333–335`). Настоящий serde-parser принял
только threshold; validate прошёл, остальные поля стали defaults:

```text
PARTIAL_PROFILE_ACCEPTED enabled=true shadow=false threshold=0.4 nonrequested_timeout=1100
```

Агент, отправляющий только изменённую ручку, может выключить shadow и включить
акустическую активацию. UI требует полный набор полей, API такого требования
не обеспечивает. Нужен строгий DTO полного профиля либо отдельный PATCH,
сохраняющий неупомянутые поля. Совместимость старого TOML не требует defaults
в сетевом DTO.

### F3 · P1 · Нативная валидация формы блокирует применение настроек

`acoustic_lab.html:326,343` помещает raw f32 из API в number input с десятичным
step; `:455` вызывает `reportValidity()` перед HTTP POST.
На живой странице шесть нетронутых полей имели `valid=false/stepMismatch=true`:
threshold, avg_threshold, score_ref, vad_noise_multiplier, vad_rise_alpha,
vad_fall_alpha. Примеры: `0.3790000081062317`, `1.149999976158142`.
Поэтому изменение другого параметра не гарантирует, что форма вообще отправит POST.
Фактический submit не выполнялся, чтобы не менять колонку.

Нужны согласованная точность отображения/step и браузерный regression test.
Нынешний Node fixture всегда возвращает true из reportValidity и пропускает дефект.

### F4 · P1 для будущего агента · Право «только Acoustic» не ограничено сервером

Веб-сервер слушает `0.0.0.0` (`src/main.rs:574`). Проверка Acoustic POST
проверяет JSON и Origin, но допускает отсутствие Origin (`src/web/mod.rs:248–255`).
Тот же dispatcher публикует system/restart, system/reboot, voice и Spotify actions.
Проверки actor/token/scopes отсутствуют; список кнопок страницы или инструментов
MCP сам по себе не ограничивает доступность остальных HTTP-операций.

Сетевые ACL/proxy вне приложения не изучались. Опасные маршруты не вызывались.
Нужен разрешённый сервером набор операций для отдельной calibration identity,
без выдачи общих SSH/HTTP/shell-инструментов. MCP-обёртка не заменяет эту границу.

### F5 · P2 · Ревизия обнуляется при рестарте

`src/acoustics.rs:68` начинает каждый процесс с revision=0. Host-fixture
изменил threshold `0.38→0.60`, пересоздал контроллер с сохранённым профилем,
затем отправил старый expected_revision=0: запрос принят и вернул threshold=0.38.
Старый клиент может перезаписать настройки после рестарта без конфликта.
Нужен instance/boot identifier вместе с revision либо устойчивая версия профиля.

### F6 · P2 · Потерянное подтверждение оставляет вечный pending

`src/acoustics.rs:130–137` объединяет timeout и закрытие oneshot. При уничтожении
request без ACK host-fixture получил `pending=true,error=None,applied_revision=0,revision=1`.
Подтверждение уже не может прийти, а следующие изменения запрещены. Нужны отдельное
состояние отказа, восстановление и тест; pending допустим лишь пока поздний ACK возможен.

### F7 · P2 · Общий epsilon скрывает допустимые изменения gain_ref

`acoustic_lab.html:175–186` использует абсолютный допуск `1e-4` для всех чисел,
но gain_ref имеет шаг `1e-5`. Временный fixture настоящего JS:
`0.2→0.20005` оставляет «Применить» выключенным и считает форму неизменённой.
Нужна точность сравнения по полю/типу, а не одинаковый epsilon для всех ручек.

### F8 · P2 · Допустимые backend-профили отклоняются интерфейсом

Строгая проверка диапазонов (`acoustic_lab.html:206`) отклоняет допустимые
f32-границы после JSON: threshold=`0.7311000227928162`, score_ref=`0.009999999776482582`.
Кроме того, backend допускает p50/average/варианты регистра, UI select и
import/export требуют только канонические options (`:202`). Fixture с p50
не смог экспортировать работающий профиль. Нужны канонизация и одинаковые
правила представления/валидации в backend и UI.

### F9 · P2 · Applied revision отображается как saved revision; восстановление затруднено

`acoustic_lab.html:284,394` показывает revision вместо applied_revision.
Fixture `revision=2,applied_revision=1,saved!=applied` показывает применённую
ревизию 2 и отключает обе кнопки возврата/применения, если форма совпадает
с applied. Возвратить рабочий профиль в сохранённый без искусственного изменения
чисел нельзя (`:262–263,497`). Нужен явный сценарий восстановления и реальные статусы.
