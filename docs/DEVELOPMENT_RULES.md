# Регламент разработки, сборки и деплоя GPT Mini

> **Главный принцип:** «одной рукой чиним — другой не ломаем».
> Ни одна работающая функция не может исчезнуть между сборками.
> Правило проверяемое: если функция не проверена командой — она не считается работающей.

Документ обязателен для агента и человека. Он же — чек-лист релиза.
Расхождения между этим документом и фактическим устройством считаются дефектом
и устраняются в том же изменении.

---

## 0. Правило нулевого шага: агент обязан найти проект

Сессия агента может быть открыта **не в корне проекта**. В таком случае
`AGENTS.md` и этот файл не попадают в контекст автоматически, и агент работает
«по памяти» — именно так терялись функции.

Перед первой правкой агент обязан:

1. Выполнить `pwd` и `git rev-parse --show-toplevel`.
2. Если корень не `/Users/oleksii/Documents/gpt-mini`, **явно прочитать**
   `AGENTS.md`, `mini-assistant/AGENTS.md` и этот файл.
3. Проверить `git status --short` в **обоих** репозиториях
   (`gpt-mini` и `mini-assistant`) и не откатывать чужие изменения.

Без этого шага результат работы не принимается, даже если код компилируется.

## 1. Единственный источник правды: коммит → сборка → хеш → деплой

Ранее сборки нельзя было сопоставить с кодом: на устройстве лежал бинарник
`52b5380…`, а какой коммит его произвёл — неизвестно.

Обязательная цепочка для каждого релиза:

```
git commit  →  ./scripts/build.sh  →  sha256  →  ./scripts/deploy.sh  →  BUILD_INFO на устройстве
```

- Деплой **запрещён** из грязного рабочего дерева без осознанного решения:
  `deploy.sh` печатает список незакоммиченных файлов и пишет `dirty` в `BUILD_INFO`.
- `/data/opt/mini-assistant/BUILD_INFO` — единственный авторитетный ответ на вопрос
  «что сейчас работает на колонке». Формат:

  ```
  commit=0116654...
  dirty=clean
  binary_sha256=52b5380...
  built_at=2026-11-09T12:00:00Z
  deployed_at=2026-11-09T12:01:00Z
  host=oleksii-mac
  ```

- Предыдущий бинарник сохраняется как `mini-assistant.prev` — это откат
  (`mv mini-assistant.prev mini-assistant` + перезапуск), а не пересборка.

## 2. Инвентарь рантайма: на устройстве не должно быть «сирот»

**Правило:** каждый файл, без которого функция работает, обязан иметь
отслеживаемый источник в git и шаг в `scripts/deploy.sh` либо `scripts/build.sh`.
Файл, существующий только на устройстве, — это дефект, а не «настройка».

Текущий инвентарь (проверяется `scripts/verify_deploy.sh`):

| Артефакт на устройстве | Источник | Кто доставляет |
|---|---|---|
| `mini-assistant` | `mini-assistant/src/**` → `build.sh` | `deploy.sh` |
| `mini_pcm_source`, `mini_pcm_sink` | C-хелперы, `.private/` + `research/` | `deploy.sh` |
| `bcm-attach` | `src/bin/bcm_attach.rs` | `deploy.sh` |
| `alarm-cli` | `src/bin/alarm_cli.rs` | `deploy.sh` (ручной шаг, см. §7) |
| `run-supervisor.sh` | `scripts/run-supervisor.sh` | `deploy.sh` |
| `config.toml`, `.env` | **только устройство**, шаблоны в git | `deploy.sh` не перезаписывает |
| `soloist-env/soloist` | официальная сборка Spotify, 90 дней | `scripts/deploy_soloist.sh` |
| `soloist-env/glibc`, `soloist-env/lib` | glibc 2.38 + apulse-шим | `scripts/deploy_soloist.sh` |
| `soloist-ctl`, `soloist-env/soloist-run.sh` | `scripts/soloist/` | `scripts/deploy_soloist.sh` |
| `keyword.rpw`, `alias-compound.rpw` | приватные, вне git | восстановление = повторная запись фразы |

Если артефакт нельзя восстановить из git и скриптов — он должен быть описан
в `docs/STATE.md` с точной процедурой восстановления (URL, версия, команда).

**Известный долг:** Soloist-окружение сейчас восстановимо только вручную,
поэтому его потеря = потеря музыки. До появления `deploy_soloist.sh` этот
пункт остаётся открытым риском и указывается в каждом отчёте.

## 3. Реестр функций (проверяется командами, а не словами)

Каждая строка — обязательная часть релиза. `verify_deploy.sh` выполняет
проверки и печатает PASS/FAIL; релиз с FAIL не принимается.

| Функция | Проверка |
|---|---|
| Голосовой диалог Gemini Live | в логе `setupComplete confirmed`, голос `Callirrhoe` |
| Регистрация инструментов | `spotify_tools: true, volume_tools: true, alarm_tools: true, weather_tools: true, ha_tools: true` |
| Wake-word «Штучка» | процесс захвата жив, `MINI_WAKEWORD_THRESHOLD=0.42`, `AVG=0.22` на устройстве |
| Отсутствие самопрерывания | в логе нет `Discarded acoustic activation` при молчащем TTS |
| Home Assistant | `HA_URL` отвечает, токен валиден (`/api/`), не только HTTP 200 страницы |
| Погода (Open-Meteo) | инструмент `get_weather` зарегистрирован |
| Будильники | `alarms.json` доступен, `alarm-cli --help` работает |
| Spotify / Soloist | `soloist ctl status` → `reachable`, `logged in: yes`, `active device: yes` |
| Громкость 0–10 | инструменты `set_volume`, `volume_up`, `volume_down` в сетапе |
| Жест ладонью (VL53L0) | `enable_ps_sensor=1`, в логе `VL53L0 ... reader active` |
| Bluetooth | `bcm-attach` жив, `hci0` присутствует |
| Супервизор | один `run-supervisor.sh`, нет дубликатов `mini-assistant` |

Отдельно: **ложный PASS запрещён**. `HTTP 200` страницы HA не доказывает
авторизацию; наличие модуля не доказывает работу; хеш без значения не evidence.

## 4. Сборка

1. `cd mini-assistant && cargo test --offline --locked` — 0 failed.
   Падение теста = стоп, а не «известный флейк».
2. `./scripts/build.sh` — Docker `messense/rust-musl-cross:armv7-musleabihf`,
   target `armv7-unknown-linux-musleabihf`. Устройство — **ELF32 armhf**,
   `uname -m` печатает `aarch64` и вводит в заблуждение: aarch64-сборка не запустится.
3. Проверка артефакта: `file` = ELF 32-bit ARM, размер ~3.2 МБ, `sha256sum` записан.
4. Запрещено деплоить бинарник, собранный не из текущего `HEAD`.

---

## 5. Деплой

1. `./scripts/deploy.sh` (сборка + загрузка) или `--skip-build` для уже собранного.
2. Деплой **атомарный**: все артефакты грузятся как `*.new`, проверяются по
   SHA256, затем одним шагом переименовываются; при расхождении хеша — выход.
3. `.env` и `config.toml` на устройстве **никогда** не перезаписываются
   автоматически. Их потеря = потеря калибровок (VAD, KWS, gain, токены).
4. После деплоя — перезапуск под супервизором и **обязательный** прогон
   `./scripts/verify_deploy.sh`. Без PASS деплой не считается выполненным.
5. Откат: `mv mini-assistant.prev mini-assistant` + `S99mini_assistant restart`.

## 6. Правила кода

1. Не ломать существующие контракты: при изменении `LiveClientConfig`,
   `AudioPlayback`, `SpotifyConfig` обновляются все конструкторы, тесты и вызовы.
2. Новый инструмент Gemini = объявление в `live_client.rs` + обработка в
   диспетчере `main.rs` + тест, что имя попало в `function_declarations`.
3. Внешний сервис не роняет ассистента: ошибка Soloist/Web API/HA/погоды
   возвращается как `status: error` с внятным текстом, процесс продолжает жить.
4. Сообщение пользователю должно называть причину. «Музыкальный сервис
   недоступен» при живом Soloist — дефект диагностики, а не ответ.
5. Никаких секретов в argv (ключ Soloist виден в `ps`), в git, в логах и в чате.
6. Абсолютные пути устройств (`/dev/input/event0`, `input0/...`) изолируются
   в одном месте и проверяются на существование; при смене нумерации функция
   деградирует с записью в лог, а не молча.
7. Показания датчика вне физического диапазона (0 мм, мусор) отбрасываются:
   нельзя превращать шум ToF в «громкость 1».
8. Отладочный уровень логов (`-v`, KWS DEBUG) — только на время диагностики:
   flash ограничен, лог растёт на мегабайты в час.

---

## 7. Git

1. Два репозитория: корневой `gpt-mini` (документы, скрипты) и
   `mini-assistant` (код). Коммит делается в том репозитории, где лежит файл.
2. Атомарные коммиты явным списком файлов, Conventional Commits.
   `git add -A` в этом рабочем пространстве запрещён.
3. Каждый релиз на устройство помечается тегом в `mini-assistant`
   (`release/YYYY-MM-DD-<sha7>`), чтобы к любому рабочему состоянию можно было
   вернуться.
4. Незакоммиченные изменения из прошлых сессий: сначала разобрать и
   закоммитить/удалить осознанно, потом начинать новую работу.
5. Хук `.githooks/pre-commit` обходить (`--no-verify`) можно только осознанно,
   с указанием причины в отчёте.

## 8. Определение готовности (Definition of Done)

Изменение готово, когда одновременно верно:

- [ ] тесты проходят (`cargo test --offline --locked`, 0 failed);
- [ ] сборка из `HEAD` собрана, хеш записан;
- [ ] `deploy.sh` доставил все затронутые артефакты (включая supervisor);
- [ ] `BUILD_INFO` на устройстве совпадает с локальным `HEAD`;
- [ ] `verify_deploy.sh` — PASS по всем функциям реестра;
- [ ] откат возможен (`mini-assistant.prev` на месте);
- [ ] изменения закоммичены в правильном репозитории, релиз помечен тегом;
- [ ] `docs/STATE.md` обновлён: что изменилось, хеш, проверки, ограничения.

---

## 9. Формат отчёта агенту

1. Что сделано и зачем (одним абзацем).
2. Фактические проверки: команда → результат (числа, хеши, PASS/FAIL).
3. Что **не** проверено и почему (например, «звук не прослушан»).
4. Открытые риски и следующий шаг.
5. Хеш артефакта и коммит — значениями, а не словами «проверено».
