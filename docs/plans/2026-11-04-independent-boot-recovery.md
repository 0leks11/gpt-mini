- Основание: запрос владельца подготовить план замены зависимой от Яндекса
  загрузки на собственную инфраструктуру.

## Результат и границы

Mini после включения от штатного БП самостоятельно подключается к домашнему
роутеру, получает адрес/маршрут/DNS и предоставляет прежний key-only SSH.
Сеть и восстановление доступа работают без `maind`, `quasar_launcher2`,
облачной модели и Pi. Голосовой процесс запускается отдельным этапом и его
отказ не должен лишать нас управления устройством.

Наш прикладной runtime остаётся на Rust и на Mini; Pi — только HA.
Стандартные Linux-компоненты `wpa_supplicant` и DHCP-клиент не переписываем
с нуля. Минимальная POSIX init-обвязка допустима как переходный механизм;
происхождение каждого системного компонента проверяем по
[целевой архитектуре](../TARGET_ARCHITECTURE.md). Это ещё не полная миграция ОС.

В этой задаче не нужны заводской сброс, приложение/аккаунт Яндекса, повторное
получение root через DNS/TLS, чужой boot image или прошивка разделов.

## Исправления к исходному предложению

1. `S10system_prep.sh`, `S40wifi.sh`, `S99mini_assistant` — пока названия ролей,
   не готовые установленные службы. Номера выбираем после проверки mounts/init.
2. В сохранённом `rcS` работает glob `/etc/init.d/S??*`; `S99mini_assistant`
   сортируется **раньше** `S99onboot.sh`. Одинакового префикса S99 недостаточно.
3. `.sh`-фрагменты исполняются внутри отдельных subshell. `export` из S10
   не подготовит окружение S40/S99; каждой службе нужны свои пути/окружение.
4. `overcommit_memory=1` разрешает выделение виртуальной памяти, но не устраняет
   нехватку RAM/OOM. Не менять его автоматически ради обещания стабильности.
5. Сохранённый `S89usbgadget` условен: наличие adbd, marker выбора network ADB,
   состояние configfs/gadget/UDC влияют на запуск. USB ADB и USB Ethernet —
   разные проверки; RNDIS на Mac не гарантирован.
6. «Интернет за 2 секунды», «0% памяти», «ни байта Яндексу» и «голубой LED
   точно означает эту ошибку» пока не доказаны.

## Этап 0. Подтвердить правильную сеть и оборудование

Из уточнения пользователя, перед работой перепроверить:

| Устройство | Адрес/идентификатор | Действие |
| --- | --- | --- |
| KN-1212 | WAN `10.77.0.138`, MAC `50:FF:20:89:31:CA` | Проверить совпадение модели/MAC; WAN не использовать для обхода admin ACL |
| KN-1212 | Прежний LAN `192.168.1.1`, ACAB | Получить доступ со стороны LAN |
| Другой Keenetic Speedster | `10.77.0.4` | Исключить из этой задачи; не пробовать наши credentials |
| Mini | Исторический MAC `B0:02:47:4C:70:56` | Искать association, lease и актуальный адрес |
| Mini | Прежний `192.168.1.110:2222` | Считать кандидатом, не доказанным текущим адресом |

Конкретные действия:

- Подключить Mac к Wi-Fi именно KN-1212; имя ACAB само по себе недостаточно.
  Подтвердить IP, default gateway, при возможности BSSID и модель в панели.
- Проверить associations и DHCP leases Mini. Сохранённая запись не считается
  активной association/арендой. Адрес Mini берём из свежей записи по MAC.
- Проверить TCP 2222 и затем key-only SSH с известным ключом и pinned host key.
  Несовпадение host key расследуем; `StrictHostKeyChecking=no` не использовать.
- Не менять WAN-admin/firewall, не добавлять port-forward и не перенастраивать
  Speedster/общую сеть. Сначала обеспечить обычный LAN-доступ к KN-1212.

**G0:** достоверно установлены наш роутер и текущий путь Mac→LAN. Доступ к
Mini может всё ещё отсутствовать — тогда переходим к этапу 1.

## Этап 1. Получить реальную консоль Mini

Проверять последовательно, без повторения одинакового неудачного опыта:

1. Если Mini есть в LAN, использовать SSH; USB для дальнейшей установки
   необязателен. Первые команды — только чтение `id`, uptime и firmware.
2. Если сети нет, проверить USB enumeration на Mac независимо от adb.
   Предыдущая смена порта/кабеля уже не дала enumeration; это отрицательное
   наблюдение, а не основание обещать ADB после ещё одного такого же действия.
3. Проверить цепь данных/питания отдельно: прямое подключение, разрешение
   аксессуара, при наличии — другой USB-хост/питаемый hub. Pi может временно
   быть диагностическим USB-хостом; это не перенос runtime ассистента на Pi.
   Достаточное питание Mac не предполагать без наблюдения стабильной загрузки.
4. Только если устройство перечисляется: проверить host adb tools и
   `adb devices -l`, затем `adb shell id`. Root-выход должен быть фактическим.
   USB Ethernet проверять отдельно по интерфейсу и маршруту; одного ADB для
   ремонта достаточно. Не открывать сетевой ADB 5555 как побочный эффект.
5. Если нет ни сети, ни USB enumeration, остановить программную установку.
   Следующая ветка — исследование boot/UART, а не удалённое выполнение команд
   по несуществующему каналу. Сначала подтвердить test pads и уровень VIO;
   возможен контактный pogo-адаптер, но готовая распиновка здесь не установлена.
   Не считать четыре пина аудиоплаты UART. Первый UART-опыт — чтение boot log,
   без подачи питания через TTL VCC, записи flash или изменения bootloader.

**G1:** есть проверяемая root-консоль и понятный способ повторно войти. Пока
её нет, можем писать и тестировать код на Mac, но не устанавливать init на Mini.
Голубой LED сам по себе не подтверждает ни загрузку Linux, ни неисправность Wi-Fi.

## Этап 2. Снять свежий baseline и подготовить восстановление

Из root-консоли собрать приватный инвентарь, не выводя credentials:

- firmware, kernel, ARM ABI; PID1, `/etc/inittab`, фактический `rcS`, список S-скриптов;
- `/proc/mounts`, mount options, устройство и filesystem `/bkupgrade`;
  тип/назначение `/data`, свободное место и момент появления mounts;
- наличие/права `wpa_supplicant`, DHCP-клиентов, SSH/adbd и нужных библиотек;
- драйвер/firmware Wi-Fi, наличие `wlan0`, backend supplicant и текущие владельцы
  интерфейса; интерфейсы, адреса, маршруты, resolver и действующие сетевые правила;
- процессы по именам, fd/listeners, `/proc/meminfo`, OOM/boot diagnostics;
- USB configfs, gadget functions, UDC, adbd и наличие управляющих markers;
- реальные init/config/binary ассистента, helper ELF/dependencies и SHA-256.

Примеры read-only команд после G1: `id`, `uname -a`, `cat /proc/mounts`,
`ls -ld /data /bkupgrade /bkupgrade/data`, `readlink /data`, `ls -l /etc/init.d`.
Доступность `ip`, `ifconfig`, `ss`, `netstat` сначала установить. Не печатать
`wpa_supplicant.conf`, .env, private keys, полное окружение и секретные argv.

Сохранить точные копии изменяемых файлов, modes/owners/symlink targets/flags
и hashes в приватный каталог на Mac и на доступный persistent storage Mini.
Зафиксировать фактически отключённые службы. Отсутствие `/data` и причину
потери Wi-Fi подтвердить здесь, а не выводить только из старого onboot.sh.

Подготовить отдельный известный rescue-набор: доступ, минимальная сеть,
свои профили/бинарники/скрипты и manifest. Если исходный baseline уже не грузит
сеть, возвращение к нему не считается рабочим recovery. Новый rescue готовим
на этапе 3 и доказываем на этапе 4, до постоянной установки. Он не должен
автоматически включать Яндекс-службы или отправлять аудио.

Установить, какие paths writable/persistent и как вернуть исходные mount flags.
Если rootfs read-only, не предполагать, что remount возможен: определить FS,
проверенный механизм записи/overlay и последствия. Не прошивать новый rootfs
как побочный эффект ремонта init.

**G2:** есть точный backup, baseline manifest и способ удержать/повторно получить
текущую root-консоль независимо от голосового приложения. Новый сетевой rescue
ещё не считается принятым. Теперь можно готовить код, но не постоянный boot.

## Этап 3. Подготовить минимальные службы и проверить offline

| Роль | Конкретный контракт |
| --- | --- |
| Подготовка data | Дождаться нужного mount; проверить `/bkupgrade/data`; создать `/data` только при его отсутствии, без замены настоящего каталога или чужой ссылки |
| USB/recovery | При необходимости поднять проверенный USB-путь; ошибки не должны зависеть от cloud/voice |
| SSH | Сохранить canonical `/bkupgrade/data/opt/mini-ssh`, host key, key-only порт 2222; не зависеть от `/data` alias, Gemini или HA |
| Wi-Fi/DHCP | Один владелец `wlan0`, один supplicant, один DHCP-клиент; собственные проверенные hooks и bounded retries |
| Ассистент | Независимый supervisor с backoff и явной readiness; его отказ не останавливает сеть/SSH |

Номера S-скриптов утвердить по свежему порядку mount/init. Каждая служба имеет
свои absolute paths, минимальное окружение, PID ownership и `start/stop/status`.
Повторный start не создаёт дубликаты; stop не применяет общий `pkill` ко всем
сетевым процессам. Ошибка/timeout не должны навсегда блокировать rcS.

Wi-Fi-подготовка:

- Проверить загрузку драйвера/firmware и появление `wlan0` без vendor daemon.
  Если это не работает, выделить отдельное исследование driver init.
- Определить рабочий backend supplicant и безопасный путь конфигурации.
  Не считать `/vendor/wpa_supplicant.conf` правильным только по имени.
- Хранить собственный профиль приватно, mode 0600; не использовать shell
  `source`/`eval`. Сохранённый профиль переносить без вывода пароля в лог.
- Выбрать один реально доступный `udhcpc` либо `dhcpcd`. Проверить его
  bound/renew/deconfig hooks: какие адреса, route и resolver он меняет,
  не вызывает ли vendor-код. Не запускать оба клиента одновременно.
- Association, DHCP, route, DNS и доступ в интернет — отдельные readiness
  состояния. Адрес `.110` получаем из DHCP/reservation, не прописываем вслепую.
- Association и DHCP имеют конечные deadlines; начальные бюджеты 30/60 с
  уточняем по измерениям. Повторные попытки — в фоне с backoff до 30 с,
  без busy loop и без зависания всего boot. Это не обещание скорости загрузки.
- Дату/TLS настраивать отдельно после сети: настоящий источник времени,
  проверка CA. Не подделывать дату и не отключать проверку сертификатов.

Offline tests до установки: mount отсутствует; `/data` уже правильный/чужой;
повторный start; неподдерживаемые утилиты; неверный профиль; partial failure;
DHCP bound→renew→deconfig; очистка только своих адресов/routes; voice crash;
облако недоступно; PID reuse. Только fixtures, без оборудования и реальных ключей.

**G3:** подготовлен воспроизводимый bundle, проведён review; offline проверки
прошли. Начальный набор не запускает микрофон, облако или HA-действия.

## Этап 4. Проверить вручную, без изменения автозагрузки

При сохранённой root-консоли и стабильном питании:

1. Загрузить staging-набор, проверить локальные/удалённые SHA-256 и права.
2. Проверить data-prep. Нельзя создавать `/bkupgrade/data` на rootfs, если
   нужный persistent filesystem не смонтирован.
3. Запустить независимый SSH и проверить вход второй сессией с прежним host key.
4. Передать интерфейс единственному Wi-Fi/DHCP-владельцу; сохранить консоль.
   Если есть прежний сетевой владелец, остановить только установленный PID/службу
   после подготовки замены и точного отката.
5. Подтвердить association на KN-1212, lease по MAC, адрес/route/DNS на Mini,
   локальный SSH с Mac и ограниченный HTTPS-запрос с проверкой сертификата.
6. Проверить DHCP renew и восстановление после краткой потери AP.
7. Снять RSS/MemAvailable/CPU; убедиться в отсутствии новых OOM событий.
   Не устраивать намеренный глобальный OOM на Mini.

До этого опыта проверить все активные capture/cloud-процессы и владельцев
аудиодескрипторов, включая оставшиеся vendor-службы. Одного выключения нашего
ассистента недостаточно для утверждения об отсутствии записи. В этом опыте
не запускать захват/передачу речи и не тестировать микрофон.
Не менять DNS/NAT на Pi или остальных маршрутизаторах. Возможные изменения
routes/resolver на Mini перечислить в [опыте](../templates/EXPERIMENT.md),
снять baseline и откатывать только собственные изменения.

**G4:** новый минимальный rescue и сеть вручную работают без Яндекса и Pi;
консоль сохранена, откат проверен. Ручной запуск после vendor init не доказывает
самостоятельный cold boot — это следующий этап.

## Этап 5. Установить пробный boot и проверить cold boot

До первой перезагрузки подготовить постоянный trial/rescue механизм.
RAM-таймер `sleep → rollback` не переживает отключение питания.

Предлагаемый контракт:

- Rescue и candidate хранятся раздельно, в versioned-путях. Candidate не
  перезаписывает binaries, профили или DHCP hooks rescue. Общие SSH host keys
  сохраняются и не меняются при переключении версий. Bootstrap/dispatcher,
  выбирающий версию, находится вне trial-набора и проверяется заранее.
- На persistent storage лежат проверенный rescue manifest, candidate manifest,
  `trial.pending` и счётчик попыток. Записи — атомарные, с подтверждённой
  durability для фактической FS; ошибки/повреждённый marker выбирают rescue.
- После mount boot-контроллер увеличивает счётчик до запуска candidate.
  Разрешить две неподтверждённые trial-загрузки; следующая выбирает rescue.
- Rescue запускает только доказанные независимые сеть/доступ, без voice и
  без автоматического возврата Яндекса. Недоступность самого data filesystem
  требует отдельного проверенного USB/UART-пути; marker этого не исправляет.
- Commit candidate выполняется из подтверждённой сессии управления после
  приёмки, с записью точного manifest/hash. PID или локальный лог «started»
  не являются основанием auto-commit.

Установить только согласованные init-файлы и их зависимости; не менять
bootloader, kernel/DTB, разделы и OTA как часть этого ремонта. Порядок:
mount/data → recovery/SSH и Wi-Fi/DHCP → readiness сети. Ассистент пока отключён.
Проверить целостность полного staging-набора до переключения единственной
точки активации. Несколько последовательных rename разных файлов не считать
атомарным деплоем. Исходные mount flags вернуть при успехе и при отказе.

Серия контролируемых cold boot на штатном БП. После каждого проверить:

- новый boot/uptime, expected mount и canonical data;
- association, DHCP, renew, DNS и key-only SSH; сохранение host key;
- отсутствие vendor daemons и отсутствие предварительного vendor init;
- отсутствие фонового voice-процесса, OOM и дубликатов DHCP/supplicant.

Порядок приёмки: две candidate-загрузки без commit → третья загрузка реально
выбирает rescue по счётчику → из проверенной консоли запустить новый trial
того же candidate/hash и проверить его загрузку → финальный commit после
проверки доступа. Подтверждать реально выбранные paths/процессы, а не только
наличие marker. Точный power-cycle сценарий и доступную консоль согласовать
перед опытом. Установка dispatcher сама требует живого rescue-пути; один
непроверенный скрипт не является страховкой от своей собственной ошибки.

**G5:** независимая загрузка сети/recovery доказана, trial принят. Обещание
«теперь всегда подключится» не заменяет отчёт с hashes и наблюдениями.

## Этап 6. Вернуть ассистент после исправления его дефектов

До запуска автоматического voice:

- Исправить общий cancellation lifecycle local barge-in/cloud interruption/
  reconnect. Повторить [подтверждённую регрессию](../REVIEW_2026-11-04_VAD_RU.md).
- Проверить конечные положительные audio-параметры и порядок PCM/end-marker.
- Явно выбрать KWS/privacy режим. VAD 10 не распознаёт «Штучка» и может
  отправить постороннюю речь; не объявлять его keyword-защитой.
- Подтвердить независимую cold-boot audio инициализацию и полный бюджет RAM,
  включая native helpers. Не переносить успешный hot-stop опыт на cold boot.
- Проверить ARM32 ELF и native dependencies; собрать новый bundle с hashes.
- Запустить только после готовности prerequisites, с restart backoff. SSH не
  перезапускается вместе с ним. Отказ cloud/HA оставляет управление Mini.

Первый согласованный голосовой тест — короткий вопрос без изменения HA.
Затем несколько ответов, interrupt→следующий ответ и reconnect. Реальные
HA-действия — отдельный ограниченный опыт с локальным allowlist. Pi не является
обязательным голосовым сервером; её отсутствие затрагивает только HA.

**G6:** голосовая функция принята отдельно от boot/network. Провайдер модели
остаётся выбором приложения; восстановление boot не требует нового аккаунта.

## Этап 7. Завершить полную замену Яндекса

Проверить состав rootfs/init, binaries, libraries/configs, DSP/controller
firmware и происхождение зависимостей; заменить оставшиеся vendor-компоненты
собственными/проверенными компонентами целевой системы. Остановка процессов
не означает их удаления. Factory kernel/rootfs также остаются отдельной частью
полной миграции, а не автоматически готовым результатом трёх init-скриптов.

Проверить фактический egress и вызовы из hooks/служб; одной DNS-блокировки
недостаточно для доказательства отсутствия обращений к Яндексу. Сбор трафика,
если потребуется, ограничить устройством, временем и размером; evidence
остаётся приватным. Не менять сетевую политику всего дома ради одного опыта.

Приёмка по H0–H7 [целевой архитектуры](../TARGET_ARCHITECTURE.md), с повторным
cold boot и проверкой обновления/отката. После приёмки можно убирать временные
зависимости; рабочий recovery остаётся.

## Подготовка и следующий шаг

Нужно: Mac с доступом к LAN KN-1212, штатный БП Mini, проверенный data-кабель,
существующие ключи Mini/known_hosts и приватное место для backup. Другой
USB-хост/питаемый hub — при наличии; UART-оснастка требуется только если
сетевая и USB-ветки исчерпаны, после проверки электрического интерфейса.

На момент создания плана сначала требовались этапы 0/1; последующая сверка
подтвердила доступ, см. актуальную таблицу по ссылке выше. До изменений boot
всё ещё нужен G2 и доказанный rescue. Оригинальная плановая работа не
устанавливала скрипты; последующие действия другого исполнителя описаны
отдельными отчётами. В этой независимой сверке устройство не изменялось.
