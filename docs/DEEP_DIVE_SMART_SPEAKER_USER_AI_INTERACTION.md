# Глубокий инженерный анализ: Физика и логика контакта пользователя с AI на умных колонках

Данный документ представляет собой детальный инженерный разбор **точки соприкосновения (Touchpoint Interface)** между человеком и искусственным интеллектом на умных устройствах.

Исследование базируется на декомпиляции и исследовании реальных конфигураций прошивки **Яндекс Станции Mini** (Amlogic A113X, `quasar.cfg`, ALSA `dmix`, `maind`), официальном коде **Amazon Alexa Voice Service Device SDK** (`FocusManager`, `AudioInputProcessor`, `AFML`), стандартах **WebRTC AudioProcessing (APM)** и архитектуре открытых проектов (**Home Assistant Wyoming Satellite**, **openWakeWord**).

---

## 1. Анатомия цикла взаимодействия «Человек — Колонка — AI»

Взаимодействие человека с умной колонкой — это строгий циклический конечный автомат (FSM), где любая ошибка в тайминге на 100 мс или неверный наклон кривой громкости разрушает ощущение «естественного интеллекта».

```text
       [1. Воспроизведение контента / Покой]
                         │
                         │ Пользователь произносит Wake-Word («Штучка»)
                         ▼
       [2. Мгновенная реакция и перебивание (Barge-In)]
       ├── Ramp Down музыки: 50–100 мс до -14 дБ (15–20% громкости)
       ├── Звуковой earcon подтверждения: spotter_start (40–80 мс)
       └── Зажигание кольца LED: latency < 30 мс
                         │
                         ▼
       [3. Захват речевой команды (Listening)]
       ├── Извлечение Pre-roll буфера: 300–400 мс аудио ДО триггера
       ├── Адаптивный VAD: отсечение остаточного фонового баса музыки
       └── Максимальное окно реплики: 8–10 секунд
                         │
                         │ Пауза в речи человека (Silence Hangover: 800–1100 мс)
                         ▼
       [4. Завершение ввода и отправка (End of Utterance)]
       ├── Маркер конца речи -> закрытие микрофонного шлюза
       └── Перевод LED в режим размышления (Pulse/Breathe)
                         │
                         │ Облачный стриминг / LLM Inference
                         ▼
       [5. Озвучивание ответа (TTS Playback)]
       ├── Подавление самоэха: блокировка VAD по энергии
       └── Разрешение перебивания ТОЛЬКО по Wake-Word
                         │
                         │ Маркер TTS Complete
                         ▼
       [6. Плавное восстановление музыки (Fade-In Recovery)]
       ├── Плавный подъем громкости музыки: 300–500 мс до 100%
       └── Гашение активной диалоговой подсветки LED
```

## 2. Фаза 1: Акустическая калибровка громкости и покой (Idle & Playback)

### Реальные измерения громкости в Яндекс Станции (из `quasar.cfg`)
В конфигурации Яндекс Станции Mini (`volume_capability.volumeDbLevels.yandexmini`) шаг громкости от 0 до 10 привязан не к абстрактным линейным процентам ЦАП, а к логарифмической шкале звукового давления (dB SPL):

```json
"volumeDbLevels" : {
   "yandexmini" : [
      31.8,  // Уровень 0 (Фоновый порог шума тракта)
      35.6,  // Уровень 1
      41.3,  // Уровень 2
      46.5,  // Уровень 3
      51.9,  // Уровень 4
      55.9,  // Уровень 5 (Комфортная громкость спокойной речи)
      61.4,  // Уровень 6
      65.0,  // Уровень 7 (Стандартный уровень будильника и напоминаний)
      69.0,  // Уровень 8
      72.6,  // Уровень 9
      74.4   // Уровень 10 (Максимальная мощность без хрипа динамика)
   ]
}
```

*Инженерный вывод:*
1. Человеческое ухо воспринимает звук логарифмически: изменение мощности звука в 2 раза воспринимается как изменение громкости всего на ~3 дБ.
2. Линейный слайдер громкости (0–100%) в софте создает провал: на 10–50% громкость почти не слышна, а на 80–100% нарастает слишком резко. Коммерческие колонки выравнивают шкалу по логарифмической кривой $V_{\text{out}} = V_{\text{max}} \cdot 10^{\frac{\text{dB} - \text{dB}_{\text{max}}}{20}}$.

### Архитектура ALSA dmix (из `/etc/asound.conf`)
На Amlogic A113X Яндекс Станции задержка аудиомикширования минимизирована:
```text
pcm.dmixer {
    type dmix
    ipc_key 1024
    slave {
        pcm "hw:0,2"
        period_size 1024     # 1024 сэмпла @ 48 кГц = ровно 21.3 мс
        buffer_size 4096     # 4096 сэмплов @ 48 кГц = 85.3 мс буфер
        rate 48000
        format "S32_LE"
        channels 2
    }
}
```
*Задержка аппаратного вывода составляет всего 21 мс*, что позволяет практически мгновенно менять громкость и вставлять звуки поверх музыки.

## 3. Фаза 2: Момент соприкосновения — Wake-Word, Barge-In и Music Ducking

Когда в комнате играет музыка на громкости 75–80 дБА, а пользователь с расстояния 2–3 метра произносит ключевое слово громкостью 60 дБА, отношение сигнал/шум составляет **`-15 ... -20 дБ`**.

### 3.1. Пауза против Приглушения (Pause vs Ducking)
В плохих реализациях голосовых колонок при детекции слова музыка ставится на жесткую паузу (`pause`).
- **Почему это ошибка:**
  1. В динамике раздается щелчок из-за резкого обрыва синусоиды.
  2. Резкая тишина в комнате создает ощущение технического сбоя («заикание»).
  3. Если слово было распознано ложно, внезапная пауза трека вызывает раздражение.
- **Стандарт Alexa и Яндекс Станции:**
  - Музыка **не останавливается**, а плавно «ныряет» под голос (Ducking).
  - Спад громкости: логарифмическая рампа (Ramp Down) длительностью **`50 – 100 мс`**.
  - Глубина приглушения: **`-14 дБ ... -18 дБ`** (до **`15 – 20%`** от текущей мощности).

### 3.2. Архитектура приоритетов каналов (AVS FocusManager)
В Amazon Alexa Client SDK реализован Activity Focus Manager (`FocusManager`), разделяющий аудио на независимые каналы с жестким приоритетом:

$$\text{DIALOG (Приоритет 1)} > \text{ALERTS (Приоритет 2)} > \text{CONTENT (Приоритет 3)}$$

```cpp
// Концептуальная логика AVS FocusManager
void FocusManager::acquireChannel(const std::string& channelName, ChannelObserver observer) {
    if (channelName == "DIALOG") {
        // Канал диалога берет безусловный FOREGROUND
        notifyObserver("CONTENT", FocusState::BACKGROUND, MixingBehavior::DUCK);
        notifyObserver("DIALOG", FocusState::FOREGROUND, MixingBehavior::PRIMARY);
    }
}
```
При переходе канала `CONTENT` в состояние `BACKGROUND` медиаплеер снижает громкость на 80%, удерживая воспроизведение.

### 3.3. Звуковой джингл подтверждения (Earcon)
Пользователь не смотрит на колонку непрерывно. Поэтому подтверждение распознавания должно быть акустическим:
- В Яндекс Станции используется файл `/system/vendor/quasar/sounds/common/spotter_start.mp3`.
- **Характеристики звука:**
  - Длительность: **`60 – 110 мс`**.
  - Частотный спектр: колоколообразный мягкий синус с центральной частотой **`1800 – 2400 Гц`** (максимальная чувствительность человеческого уха).
  - Уровень громкости: нормализован относительно текущей громкости станции (`-6 dBFS`).
  - Воспроизводится параллельно с началом спада музыки, подтверждая захват внимания.

## 4. Фаза 3: Активное слушание и захват речевой команды (Listening Phase)

### 4.1. Пре-ролл буфер (Pre-Roll Buffer)
Человек говорит естественно: «Штучкакакаяпогодазавтра» без искусственных пауз.
- Детектор ключевого слова (Rustpotter / Spotter) подтверждает слово только на его последнем согласном звуке (на букве «а» в слове «Штучк-а»).
- К моменту подтверждения первое слово команды («какая») уже частично началось.
- **Решение:** В оперативной памяти всегда поддерживается кольцевой Pre-roll буфер длительностью **`300 – 500 мс`** (для 16 кГц 16-бит моно это `9600 – 16000 байт`).
- В момент срабатывания триггера в облако/LLM первым делом отправляется весь Pre-roll буфер, а затем текущий поток. Это гарантирует 0% срезанных слогов.

### 4.2. Поведение VAD при приглушенной музыке
При играющей фоном музыке стандартный статический VAD по энергии захлебывается низкими частотами баса (kick / sub-bass).
- В Яндекс Станции и WebRTC APM аудио перед VAD проходит через полосовой фильтр, отсекающий частоты ниже 150 Гц.
- В `mini-assistant` реализован адаптивный динамический порог:
  $$\text{Threshold}_{\text{dyn}} = (\text{NoiseFloor} \cdot 1.15 + 10.0).\text{max}(\text{BaseThreshold})$$
  Во время музыки `NoiseFloor` отслеживает уровень фонового трека и приподнимает планку срабатывания, благодаря чему VAD реагирует только на голос человека.

## 5. Фаза 4: Отсечение тишины и окончание фразы (Silence Hangover & End-of-Speech)

Самый тонкий момент в эргономике: как понять, что человек закончил говорить, не заставляя его ждать и не обрывая на полуслове?

### Временная матрица таймингов тишины

```text
Пользователь говорит: [..."включи свет в коридоре"] ──> Пауза ──> [Тишина]
                                                           │
        0 ms ─────────────── 350 ms ────────────── 900-1100 ms ───────────── 1800 ms
                             ▲                     ▲                        ▲
                    Естественная микропауза   Оптимум End-of-Speech   Initial Silence Timeout
                    (вдох, подбор слова)      (Генерация ответа)      (Если ничего не сказали)
```

1. **Микропаузы внутри речи (`150 – 350 мс`):**
   - Человек делает паузы между словами для вдоха или размышления. Детектор обязан удерживать состояние `has_spoken = true` и не закрывать шлюз.
2. **Окно фиксации окончания фразы (`Silence Timeout / Hangover`):**
   - **`800 – 1100 мс`** — отраслевой стандарт (Google Assistant, Alexa, Алиса).
   - *Меньше 600 мс:* колонка перебивает медленно говорящих людей или пожилых пользователей на полуслове.
   - *Больше 1500 мс:* колонка кажется «тупой и заторможенной», повисает неудобная пауза.
3. **Начальный таймаут тишины (`Initial Silence Timeout`):**
   - Если пользователь позвал ассистента («Штучка!»), прозвучал джингл, но в течение **`1500 – 1800 мс`** человек не произнес ни слова:
   - Сессия мягко аннулируется, звучит тихий сигнал отмены (`spotter_cancel.mp3`), и музыка плавно возвращается на 100%.

## 6. Фаза 5: Озвучивание ответа и голосовой арбитраж (TTS & Self-Barge-In)

### 6.1. Акустическое самоперебивание (Self-Interruption Problem)
Когда умная колонка отвечает собственным синтезированным голосом (TTS) через свой же динамик:
1. Звук голоса ассистента попадает прямо в микрофоны с уровнем до 70–80 дБА.
2. Если в этот момент активен VAD по энергии, колонка «услышит саму себя», решит, что пользователь продолжает говорить, и закольцует сессию в бесконечный шум.
- **Решение в кодовой базе:**
  - Во время воспроизведения TTS и в течение **`800 мс`** после его окончания (хвост реверберации помещения) VAD по энергии **жестко заблокирован**.
  - Буфер предзаписи непрерывно очищается (`gate.sanitize_pre_roll()`), чтобы эхо не попало в следующий запрос.

### 6.2. Перебивание ассистента человеком (Barge-In during TTS)
Что если ассистент начал длинный ненужный ответ, и человек хочет сказать «Штучка, хватит»?
- Во время TTS разрешена работа **только детектора ключевого слова (Rustpotter / Spotter)**.
- При фиксации слова «Штучка» на фоне собственного голоса:
  1. Вызывается немедленный `playback.interrupt()` — ЦАП и PCM-синк мгновенно сбрасываются.
  2. В сокет Gemini Live отправляется маркер отмены `clientContent { turnComplete: true }`.
  3. Открывается новый виток диалога для свежей команды.

### 6.3. Плавный возврат музыки (Music Recovery Ramp)
После завершения реплики ассистента музыка восстанавливается:
- Время плавного подъема (Ramp Up): **`300 – 500 мс`**.
- Плавный подъем исключает резкий звуковой удар по ушам и звучит профессионально.

## 8. Архитектурный план улучшений для GPT Mini

Чтобы довести поведение **GPT Mini** до стандартов коммерческих флагманов, сформирован конкретный план модернизации модулей в `mini-assistant`:

1. **Модуль `MusicDucker` (`src/spotify/ducking.rs`):**
   - Заменить резкое ступенчатое переключение громкости на плавную интерполяцию громкости по таймеру (3 шага с интервалом 25 мс: 100% -> 60% -> 35% -> 20%).
2. **Модуль `InputGate` (`src/wakeword/mod.rs`):**
   - Утвердить Pre-roll буфер на уровне **`400 мс`**.
   - Настроить тайминг окончания фразы на **`1100 мс`** (идеальный баланс между терпеливостью к паузам и быстротой ответа).
3. **Модуль звуковых сигналов (Earcons):**
   - Внедрить воспроизведение ультракороткого синтезированного звукового импульса колокольчика (chime) в момент распознавания вейкворда, чтобы пользователь сразу слышал готовность колонки слушать.
4. **Светодиодное кольцо SN3236 (`src/web/mod.rs`):**
   - Синхронизировать мгновенное включение акцентного цвета (Emerald/Azure) за `< 20 мс` при детекции слова с плавным затуханием (fade-out) после завершения взаимодействия.
