# Рабочий цикл

## 1. Уточнить результат

Определить пользовательский сценарий и проверяемые критерии готовности.
Отделить неизвестный механизм, который надо исследовать, от уже понятной
функции, которую надо реализовать. Для исследования заранее определить,
какое наблюдение подтвердит или опровергнет гипотезу.

Прочитать правила, код и существующие изменения. Проверить, в каком из двух
Git-репозиториев выполняется работа. Зафиксировать исходные поломки проверок,
чтобы не приписывать их новой правке и не скрывать их.

## 2. Спланировать

Существенная задача получает файл `docs/plans/YYYY-MM-DD-topic.md` в своём
репозитории по [шаблону](templates/PLAN.md). В нём нужны:

- ожидаемое поведение и критерии приёмки;
- контракт данных, состояния, ресурсы и ошибки;
- небольшие последовательные шаги;
- проверка каждого изменённого контракта;
- откат и открытые вопросы.

Для сетевого аудио явно описывать формат PCM, framing, deadlines, буферы,
backpressure, CANCEL, EOF и reconnect. Для HA — разрешённые операции,
аутентификацию, timeout и исключение повторного выполнения после ошибки.
Для модели — место вычислений, измеряемую задержку и границы контекста.

## 3. Реализовать и проверить

Работать небольшими связными изменениями. Для исправления сначала получить
воспроизводимый отказ или regression test, если это практично. Проверять
результат по [матрице](TESTING.md); внешний API и оборудование не нужны для
чистого парсера, state machine или документации.

Тесты не должны сами включать кондиционер, выключать штатные службы или
отправлять настоящую речь. Интеграционные сценарии выделять отдельно от
default suite. Если проверка недоступна, записать причину и непроверенное
свойство; не заменять это формулировкой «всё работает».

## 4. Провести ревью

Пройти [чек-лист](CODE_REVIEW.md) по финальному diff. Для сложных протоколов,
доступа и live-изменений полезен второй агент с отдельной задачей ревью.
Он изучает итоговый код и доказательства, а не только описание автора.

Закрыть дефекты корректности и безопасности до объявления готовности.
Оставшиеся ограничения должны быть видны в результате, а не только в переписке.

## 5. Сохранить результат

Обновить план и при необходимости [STATE](STATE.md). Архитектурный выбор
записать отдельным ADR по [шаблону](templates/DECISION.md): причина,
альтернативы, последствия, статус. Старые результаты не переписывать как новые.

Перед коммитом посмотреть `git diff`, затем добавить только свои файлы,
проверить `git diff --cached --check` и весь staged diff. Коммит:
`type(scope): краткое действие`; типы `feat`, `fix`, `test`, `docs`, `refactor`,
`build`, `ci`, `chore`. Не создавать ветки `dev` или PR без необходимости.
Push и deployment — отдельные действия; локальный коммит их не выполняет.
