# Плейбук Hillclimb для акустической калибровки и M-AEC в GPT Mini

Этот документ определяет регламент систематической, итеративной оптимизации акустических параметров и алгоритмов эхоподавления (M-AEC) на умной колонке **GPT Mini** с подключённой внешней активной акустикой (KRK Systems 60W).

---

## 1. Фундаментальный принцип

Оптимизация ведётся строго по циклу:
$$\text{Гипотеза} \longrightarrow \text{Точечное изменение} \longrightarrow \text{Замер на замороженном стенде} \longrightarrow \text{Анализ спектрограммы/метрик} \longrightarrow \text{Сохранение (KEPT) или Откат (REVERTED)}$$

- **Никаких слепых изменений:** Любое улучшение должно подтверждаться числовым сдвигом целевой метрики сверх уровня шума и зелёными регрессионными тестами.
- **Откат безопасен:** Статистика, сырые логи, спектрограммы и diff отклонённых гипотез никогда не удаляются, а сохраняются в изолированной структуре `.hillclimb/`.

---

## 2. Структура Out-of-Tree данных (`.hillclimb/`)

Папка `.hillclimb/` изолирована в `.gitignore` обоих репозиториев (`gpt-mini` и `mini-assistant`), что гарантирует сохранность данных при `git restore` или переключении веток.

```text
.hillclimb/
├── decision.tsv               # Сводный журнал всех попыток (TSV)
├── runs/                      # Сырые дампы замеров и полные логи выполнения
│   ├── run_001_raw.json
│   ├── run_001.log
│   └── last_run.log
├── patches/                   # Сохранённые diff отклонённых гипотез
│   └── exp_003_failed.patch
└── spectrograms/              # Спектрограммы (SVG и JSON матрицы) до/после
    ├── run_001_stft_matrix.json
    └── run_001_waterfall.svg
```

### Формат журнала `decision.tsv`:
Колонки разделяются символом табуляции (`\t`):
1. `id` — порядковый номер (например, `001`, `002`);
2. `timestamp` — время проведения эксперимента в ISO 8601;
3. `hypothesis` — формулировка архитектурной причины гипотезы;
4. `files_changed` — точный список затронутых файлов или параметров;
5. `baseline` — значение целевой метрики до изменения;
6. `result` — полученное значение метрики;
7. `delta_%` — относительное изменение в процентах;
8. `tests` — статус прогона регрессионных тестов (`PASS` / `FAIL`);
9. `status` — вердикт: `KEPT` (принято) или `REVERTED` (отклонено);
10. `commit_or_patch` — хэш коммита в Git либо имя сохранённого патча;
11. `notes` — ключевые наблюдения (резонансы, артефакты на спектрограмме).

## 3. Целевые метрики и замороженные измерители (Measurement Harness)

Для каждого направления оптимизации фиксируется ровно **одна главная метрика**:

| Задача | Главная метрика | Измерительный харнесс | Критерий улучшения |
|---|---|---|---|
| **AEC (Эхоподавление)** | **ERLE (дБ)** (Echo Return Loss Enhancement) | Свип/музыка через `KRK Systems` при замере микрофонного массива `hw:0,2` | Рост ERLE $\ge +1.5\text{ дБ}$ без слышимых искажений речи |
| **Barge-in (Слово вызова)** | **$F_1$-score под музыкой** при громкости 75–85 dBA | Воспроизведение тестового датасета голосовых фраз во время музыки | Рост $F_1 \ge +0.05$, ложные срабатывания $\le 1\text{ на 24ч}$ |
| **Акустический профиль (EQ)** | **Candidate Score** ($F_1$, шум, задержка) | 6-полосный спектральный анализ STFT + VAD/KWS валидатор | Превосходство над baseline score |

**Правило заморозки:** Измерительный скрипт закоммичен в репозиторий до начала серии экспериментов. Изменение скрипта замера аннулирует предыдущую историю замеров.

## 4. Визуализация и наблюдаемость (Spectrograms & Logs)

Агент и инженер должны видеть динамику процессов как во временной, так и в частотной области:

1. **Спектрограммы Waterfall (SVG/Canvas):**
   - 2D-карты частот (100–8000 Гц) по времени:
     - Канал микрофона (Mic Array Beamformed);
     - Канал опорного сигнала loopback (TDMIN_B);
     - Канал сигнала ошибки (AEC Output / Residual).
   - Наглядно показывают полосы, где адаптивный фильтр подавил эхо, и гармоники, пробивающиеся через фильтр (нелинейности динамика).
2. **Структурированные матрицы STFT (JSON):**
   - Энергия по 6 частотным диапазонам:
     - `Sub-bass` (60–180 Гц)
     - `Low-mid` (180–500 Гц)
     - `Mid` (500–1500 Гц)
     - `Presence` (1500–4000 Гц)
     - `Brilliance` (4000–8000 Гц)
   - Позволяют AI-агенту программно выявлять резонансные пики корпуса или внешней базы.
3. **Доступность данных:**
   - Локально на диске: `.hillclimb/spectrograms/` и `.hillclimb/runs/`
   - Через REST API: `GET /api/v1/acoustics/samples/{id}/spectrogram`
   - Через MCP-сервер: инструмент `get_spectrogram(sample_id)` для прямого вызова LLM-агентом.

## 5. Протокол безопасной итерации (Safe Iteration Loop)

```text
                  ┌──────────────────────────────────────────────┐
                  │ 1. Прочитать decision.tsv и спектрограмму    │
                  │    Сформулировать обоснованную гипотезу      │
                  └──────────────────────┬───────────────────────┘
                                         │
                                         ▼
                  ┌──────────────────────────────────────────────┐
                  │ 2. Внести точечное изменение                 │
                  │    (код или параметры config.toml)           │
                  └──────────────────────┬───────────────────────┘
                                         │
                                         ▼
                  ┌──────────────────────────────────────────────┐
                  │ 3. Запустить замер (медиана N прогонов)      │
                  │    Сохранить лог в .hillclimb/runs/          │
                  │    Сгенерировать спектрограмму в .hillclimb/ │
                  └──────────────────────┬───────────────────────┘
                                         │
                 ┌───────────────────────┴───────────────────────┐
                 │ Метрика выросла И тесты check.sh зелёные?     │
                 └───┬───────────────────────────────────────┬───┘
                     │ ДА                                    │ НЕТ
                     ▼                                       ▼
      ┌───────────────────────────────────┐   ┌────────────────────────────────┐
      │ • Записать в decision.tsv (KEPT)  │   │ • Сохранить diff:              │
      │ • git add <файлы>                 │   │   git diff > .hillclimb/       │
      │ • git commit -m "feat/fix/perf..."│   │              patches/exp_N.patch│
      │ • git push origin main            │   │ • Записать в decision.tsv      │
      │ • Обновить baseline               │   │   (status = REVERTED)          │
      └──────────────────┬────────────────┘   │ • Точечный откат:              │
                         │                    │   git restore <файлы>          │
                         │                    └───────────────┬────────────────┘
                         │                                    │
                         └──────────────────┬─────────────────┘
                                            │
                                            ▼
                              ┌───────────────────────────┐
                              │ Предикат остановки        │
                              │ (цель выполнена/плато)?   │
                              └───────────────────────────┘
```

## 6. Преодоление плато

Если 3 итерации подряд получают статус `REVERTED`:
1. **Смена оси поиска:** переход от временных параметров ($\tau_{\text{bulk}}$) к частотным коэффициентам регуляризации ($\epsilon$, $\mu$, утечка $\lambda$).
2. **Анализ спектрограммы остаточного эха:** поиск гармонических искажений на низких частотах (< 200 Гц), требующих включения нелинейного постфильтра (RES Wiener).
3. **Синтез патчей:** ревизия сохранённых в `.hillclimb/patches/` отклоненных идей — иногда комбинация двух субпороговых правок даёт синергетический эффект.
